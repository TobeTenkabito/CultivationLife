# 第6、7步：V1导入与影子运行

## 第6步：一次性旧存档导入

入口为`V2GameEngine.import_v1_save()`，命令行入口为：

```powershell
python tools/import_v1_save.py data/saves/<存档ID>.json `
  --database data/v2/saves.sqlite3 `
  --report data/v2/import-reports/<存档ID>.json
```

导入器只解析原始JSON，不导入或执行V1的`GameEngine`、`GameState`、存档迁移、DLC或事件代码。源文件始终只读；目标存档通过SQLite事务一次写入，验证失败时不会留下半份V2存档。

当前可靠迁移范围：

- 玩家身份、年龄、寿元、生死状态；
- 境界、层数、道统、灵根、气息经验、机缘、心魔、突破瓶颈；
- 已知功法与主修功法；
- 当前世界和地图位置；
- 有V2定义的普通行囊物品；
- 道侣、好友、师徒、侍妾及其规范人物实体；
- 当前势力成员身份、势力内贡献及玩家创建势力的控制权；
- 当前生命/法力比例；
- 首批鬼修、妖修DLC状态。

每次导入会记录源文件SHA-256、源/目标存档ID、V1格式版本、迁移数量和逐字段警告，并追加`migration.v1.imported`事件。无法识别的物品、功法、地点和尚未迁移的系统不会静默消失，都会进入报告；原始值仍保留在未改动的V1文件中。

首次导入返回报告；之后可用`V2GameEngine.legacy_import_report(game_id)`从V2存档内的审计组件重新读取。同一源文件不能凭借更换目标ID重复导入同一个SQLite库。

### 主动阻断条件

以下状态目前无法忠实落到V2，导入会在写数据库前失败：

- 尚未结算的事件；
- 正在进行的突破试炼；
- 监禁、修为封印或拘魂控制；
- 拍卖中仍冻结的玩家竞价或寄拍资产；
- 未知道统、灵根、境界或当前世界；
- 存活人物已经达到寿限等源存档核心矛盾。

这不是V1/V2双向同步。导入后的V2存档不会写回V1格式。第9步的批量导入前备份尚未启用，因此正式切换前仍不得删除V1存档目录。

## 第7步：相同种子影子运行

影子运行器位于`cultivation_life.migration`，这是唯一允许同时依赖V1和V2的集成边界。V2运行时仍保持对旧引擎、旧模型和旧存档类的零依赖。

示例：

```powershell
python tools/run_v1_v2_shadow.py `
  --seed 123 `
  --command rest:1 `
  --command cultivate:2 `
  --report build/shadow/seed-123.json
```

当前共享命令面为`cultivate`和`rest`，参数使用行动单位，而不是直接传入年数。运行器为两套引擎建立隔离存档，按顺序执行相同命令，并在创建后及每条命令后采集语义快照。

比较项包括：

- 身份、年龄、寿元、生死；
- 道统、灵根、境界、层数、机缘；
- 世界与地点；
- 行囊汇总；
- 关系类型计数；
- 当前势力及贡献；
- 是否存在待处理事件。

内部实体ID、事件ID、SQLite修订号、时间戳和随机数序列化不参与比较。报告中的`error`代表核心行为契约偏差，`warning`代表平衡数值或尚待迁移的玩法差异。影子运行不会自动判定哪一侧正确；它提供稳定、可复现的证据，供第8步功能矩阵逐项确认。

目前已能稳定发现一个真实差异：V1新角色自带普通灵剑，V2新角色行囊为空。该差异会以`economy/inventory`警告出现，而不会因两边随机存档ID不同产生噪声。
